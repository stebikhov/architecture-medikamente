# Задание 6. Классификация данных перед загрузкой в хранилище

Диаграмма C2 движка: [c2-classification-engine.drawio](c2-classification-engine.drawio) — уровень C2 (контейнеры развёртывания, на диаграмме они пронумерованы E1–E12, в скобках указана технология). Состав контейнеров совпадает с L3-компонентами Task2 и не пересекается с классами данных C1–C6 из Task3. Целевая архитектура: [../Task2/c4-target.drawio](../Task2/c4-target.drawio) и [../Task2/README.md](../Task2/README.md). Классы и теги: [../Task3/data-protection.md](../Task3/data-protection.md).

## 1. Что проектируем

Движок стоит между источниками (1С, Excel на общем диске, БД портала, сканы медицинских документов) и аналитическим хранилищем ClickHouse. Между ними лежит **staging-область вне хранилища** (шифрованное объектное хранилище, TTL 24 часа). Сырые данные попадают туда до классификации, а в Landing внутри ClickHouse уходит уже размеченный пакет. Так выполняется требование «классификация до загрузки в хранилище»: неклассифицированных данных в ClickHouse нет ни на одном слое. Движок работает пакетами и решает четыре задачи:

1. **Обнаружение структуры.** Входные структуры меняются, поэтому есть реестр схем. При новом поле, переименовании или смене типа затронутые поля классифицируются заново.
2. **Классификация.** Правила по шаблонам (телефон, паспорт, ИНН, СНИЛС, email) дополняет NER-модель для свободного текста (анамнез, заключения) и OCR-контур для сканов. Каждому полю присваивается уверенность.
3. **Разметка и маршрутизация.** Поля получают один из шести тегов Task3 §1.2 (Публичные, Внутренние, ПД(общие), ПД(здоровье), ПД(фин.), Секреты), и запись уходит в зону по тегу (таблица ниже). Поля с низкой уверенностью или без тега попадают в карантин. Длинные тексты, которые ждут асинхронной NER-классификации, находятся в отдельном состоянии «в очереди на классификацию» и карантином не считаются.
4. **Прослеживаемость.** Теги, владелец и происхождение (lineage) наборов данных хранятся в OpenMetadata.

По умолчанию данные конфиденциальны, пока классификатор не подтвердит обратное. Пустой тег означает карантин.

Маршрутизация тега в зону:

| Тег | Класс | Зона |
| --- | --- | --- |
| Публичные | C1 | Anonymized (без ограничений) |
| Внутренние | C2 | Pseudonymized |
| ПД(общие) | C3 | Pseudonymized; прямые идентификаторы — Restricted |
| ПД(здоровье) | C4 | Restricted |
| ПД(фин.) | C5 | Restricted |
| Секреты | C6 | Не загружается в аналитику: блокировка и алерт ИБ |
| нет тега, низкая уверенность | — | Карантин |

Номер банковской карты (PAN) не размечается как ПД(фин.) и в зону не маршрутизируется: Task3 запрещает его хранение. Правило для номера карты (шаблон из 16 цифр с проверкой контрольной суммы по алгоритму Луна) блокирует поле и поднимает алерт ИБ. Значение удаляется из staging, остальные поля пакета идут по обычному маршруту.

Если для одного поля срабатывают несколько правил (например, 10 цифр подходят и под паспорт, и под ИНН), конфликт разрешается по порядку:

1. Название и тип колонки («паспорт», «ИНН», «серия», «номер»).
2. Соседние поля записи: рядом дата выдачи, код подразделения и ФИО указывают на паспорт, рядом наименование организации — на ИНН.
3. Уверенность правил (у правила для паспорта РФ 0,97, у правила для ИНН 0,90).

Если после трёх шагов разница уверенности меньше 0,1 и решение остаётся неоднозначным, поле получает более строгий из двух тегов и уходит в карантин. Оба варианта относятся к классу ПД(общие), поэтому ошибка выбора не меняет зону, а только метку правила.

## 2. Входные данные и покрытие источников

В As-Is часть данных приходит таблицами, часть сканами, и движок должен брать оба типа.

| Источник                              | Формат                                              | Тип обработки                           | Особенность                                                                                                                   |
| ------------------------------------- | --------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 1С:Бухгалтерия (выгрузка)             | Табличные выгрузки (XLSX/CSV)                       | Правила по колонкам + проверка шаблонов | Структура стабильна, но названия колонок меняются при обновлении 1С                                                           |
| 1С:Торговля и склад                   | Табличные выгрузки                                  | Правила                                 | Ожидается класс Внутренние                                                                                                    |
| Excel-файлы на общем диске            | Произвольные XLSX, один файл на журнал или пациента | Правила + NER для текстовых колонок     | Заголовки и состав колонок нестабильны, главный источник дрейфа схем                                                          |
| БД портала (записи, договоры)         | Выгрузка PostgreSQL (CDC или ночной дамп)           | Правила                                 | Структура контролируема, но поля расширяются по мере MVP                                                                      |
| Медицинские карты и анализы           | JPG, PDF, TIFF (сканы)                              | OCR-контур → текст → NER → правила      | Основной носитель специальной категории; OCR ошибается, поэтому распознанный текст проверяется правилами по шаблонам          |
| Реестр лаборатории  | XLSX                                                | Правила + NER                           | Внешний формат, меняется без предупреждения                                                                                   |
| Расчётные листки, заявки              | XLSX                                                | Правила                                 | Класс C3, кадровые данные                                                                                                     |

OCR-контур входит в состав движка: скан → распознавание (Tesseract / ABBYY) → нормализация → классификатор. Для источников C4 (медкарты, анализы) выполняется полный OCR каждой страницы. Выборочный OCR (первая страница, поиск по шаблону) применяется только к большим архивам. Нераспознанные страницы остаются в staging до истечения TTL и в Landing не попадают; повторное распознавание запускается до истечения TTL, иначе страница уходит на ручную обработку. Поля с низкой уверенностью распознавания направляются в карантин тем же механизмом, что и поля с низкой уверенностью классификации, пороги разные.

## 3. Слои хранилища для конфиденциальных данных

Часть данных в хранилище конфиденциальна, поэтому зоны разделены по уровню защиты.

| Зона                         | Что хранится                                               | Доступ                                                        | Защита                                                                                   |
| ---------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Staging (вне ClickHouse)     | Сырые пакеты до классификации, TTL 24 часа                 | Только загрузчик и сервисная роль движка; человеку недоступно | Шифрованное объектное хранилище (S3-совместимое), SSE-KMS, отдельный DEK, журнал доступа |
| Landing (в ClickHouse)       | Пакеты после классификации, короткий срок (TTL 7 дней)     | Только загрузчик и Data steward (специалист по качеству и классификации данных); C4 он видит по процедуре двух ключей | AES-256-GCM при хранении, ключи из KMS, DEK на пакет                                          |
| Restricted                   | C4, C5 и прямые идентификаторы C3                          | По ABAC через OPA, только с обоснованием цели                 | Полевое шифрование, DEK на субъекта и отдельные политики, аудит каждого чтения           |
| Pseudonymized                | ПДн, заменённые токенами                                   | Аналитики по роли, через query gateway                        | Токенизация, маскирование, row policies                                                  |
| Anonymized                   | Агрегаты, k-анонимные выборки (k ≥ 5) для BI, ML и LLM     | Широкий круг пользователей                                    | Обезличивание, дифференциальная приватность для агрегатов                                |

Карантин — управляемое состояние вне аналитических зон, из двух частей:

- Очередь карантина в движке (контейнер E9 «Очередь карантина» и UI steward на диаграмме C2): пакеты и поля, для которых не получен тег или уверенность ниже порога. Значения в очереди маскируются, полное значение C4 доступно только с подтверждением двух человек. Действия steward журналируются. Значения в очереди не токенизированы, это важно при удалении данных по запросу субъекта.
- Изолированная таблица карантина в хранилище (хранилище карантина на стр. 2 диаграммы Task2): содержимое непомеченных полей. У аналитиков доступа к ней нет, ключа секции Anonymized для неё тоже нет.

Карантин живёт по таймеру. TTL — 14 дней с момента попадания поля в очередь. SLA ревью — 2 рабочих дня с постановки в очередь, это время учитывается отдельно от TTL, чтобы эскалация срабатывала раньше истечения. Если TTL истёк, поле не удаляется молча: steward получает эскалацию, а пакет, к которому относится поле, блокируется для выгрузки до решения. Метрика «возраст самого старого поля в карантине» показывает, не копится ли неразобранное.

Отдельно от карантина существует состояние «в очереди на классификацию»: длинный текст принят, но ждёт асинхронного прогона NER. В этом состоянии поле уже имеет предварительный тег от правил, а NER уточняет его. Оно не считается карантином и не входит в метрику доли карантина, но учитывается в задержке классификации.

Кроме зон, действуют такие меры:

- **Теги в каталоге.** У каждой таблицы и поля есть тег и владелец в OpenMetadata, тег используется в политиках доступа.
- **Row-level и column-level политики.** Ограничивают доступ по строкам и колонкам, даже если таблица одна.
- **Раздельные ключи.** Envelope-схема: KEK на зону в KMS/HSM. DEK — на субъекта для Restricted (нужен криптошрединг по DSAR) и на пакет для Landing и Pseudonymized. Компрометация одного DEK остальные данные не раскрывает.
- **Маскирование в Landing.** Steward видит пакет только в маскированном виде. Полное значение C4-поля доступно только с подтверждением двух человек, как и в Restricted. Иначе Landing стал бы обходным путём к данным, закрытым в Restricted. Те же условия действуют в карантине и в каталоге, поэтому все три места покрыты одним правилом.
- **Запрет выгрузки из Restricted.** Выгрузка возможна только в Pseudonymized через процедуру обезличивания.
- **Срок хранения.** TTL на уровне ClickHouse для Landing, для остальных зон по политике.

## 4. Эталонная размеченная выборка (golden set)

Recall и precision считаются по данным, размеченным вручную, поэтому без эталона их не измерить. Эталон входит в обязательные артефакты проекта.

### 4.1. Состав

| Страта                                        | Объём | Что покрывает                                           | Ожидаемый класс                     |
| --------------------------------------------- | ----- | ------------------------------------------------------- | ----------------------------------- |
| Записи пациентов                              | 600   | ФИО, телефон, email, дата рождения, адрес, место работы | ПД(общие), частично ПД(здоровье) |
| Договоры                                      | 300   | Паспортные данные, реквизиты, подписи                   | ПД(общие)                        |
| Медкарты и заключения (свободный текст)       | 800   | Анамнез, диагнозы, жалобы, назначения                   | ПД(здоровье)                        |
| Сканы после OCR, обычное качество             | 200   | Медкарты и бланки анализов в виде изображений           | ПД(здоровье)                        |
| Платёжные и кадровые                          | 300   | Суммы, реквизиты, оклады, ФИО сотрудников               | ПД(фин.), ПД(общие)        |
| Технические и внутренние (негативные примеры) | 300   | Расписания, тарифы, ТМЦ, идентификаторы оборудования    | Внутренние, Публичные             |
| Сложные OCR (отдельная страта)                | 200   | Сканы с низким качеством распознавания                  | ПД(здоровье)                        |
| Итого                                         | 2 700 | 2 500 полей основного эталона и 200 полей «сложных OCR» | —                                   |

Состав C4: 1 200 полей (800 текстовых и 400 OCR). Положительных примеров C4 в основном эталоне 1 000 (800 текстовых и 200 OCR). Ещё 200 сложных OCR-полей размечены вручную и остаются в эталоне отдельной стратой, а не вычёркиваются: исключение трудных примеров завышало бы recall. Метрики по ним публикуются отдельно, и общий recall C4 по всем 1 200 полям тоже приводится.

Объём выбран по статистике. При 1 000 положительных примерах C4 и нуле ошибок консервативная оценка по правилу трёх даёт recall не ниже ≈ 99,7 %, при 200 примерах — только ≈ 98,5 %. Для OCR-страты этого недостаточно для цели «≥ 99 %», поэтому для сканов задана отдельная, более мягкая цель: recall ≥ 97 % на обычных сканах и ≥ 90 % на «сложных OCR» без блокировки релиза, но с обязательным разбором ошибок. Жёсткая цель ≥ 99 % относится к текстовым C4-полям (800 примеров, нижняя граница ≈ 99,6 %). Подъём OCR-страты до 1 000 полей возможен после накопления размеченных сканов из карантина. Метрики публикуются с доверительным интервалом.

Негативная страта нужна, чтобы классификатор не учился «находить хоть что-нибудь» и не забивал карантин.

Эталон собран стратифицированно, поэтому precision на нём нельзя переносить на прод: доли классов в стратах не равны долям в реальном потоке. Для precision в проде используется отдельная случайная выборка из рабочего потока, которую steward размечает регулярно (см. §5).

### 4.2. Процесс разметки

1. **Разметка.** Два разметчика независимо размечают одну выборку по классификации Task3 §1.2 (класс, тег, зона). В условиях задачи Data steward (специалист по качеству и классификации данных) один (бизнес-аналитик, Task5 §5), поэтому второй разметчик и ML-инженер для NER — допущение: это найм, и в списке ролей Task5 §5 их надо добавить. Запасной вариант: первый разметчик — бизнес-аналитик, второй — врач (медицинский руководитель назначает специалистов), а спорные случаи разбирает технический директор.
2. **Согласование.** Расхождения разбирает технический директор, решение фиксируется в реестре решений. Согласованность измеряется каппой Коэна, цель κ ≥ 0,8.
3. **Заморозка.** Согласованная выборка становится эталоном версии 1. Менять эталон можно только по решению технического директора и с новым номером версии.
4. **Пополнение.** Поля из карантина с низкой уверенностью идут в очередь на разметку, размеченный пример возвращается в эталон. Цикл замкнутый: качество растёт по мере накопления ошибок.
5. **Переоценка.** Метрики по эталону пересчитываются полностью при каждом релизе правил и моделей.

### 4.3. Хранение и доступ

- Отдельное хранилище «golden set», доступ только у разметчиков (двух человек) и технического директора.
- Данные эталона по возможности обезличиваются: для правил по шаблонам хватает синтетических значений, для NER берутся обезличенные фрагменты реальных заключений.
- Эталон версионируется в одном репозитории с правилами, поэтому изменения правил и эталона видны в одном diff.

## 5. Метрики эффективности классификации

Метрики по классам задаются отдельно: общий F1 не показывает, где именно теряются поля C4. Precision, recall и F1 считаются для C3, C4, C5, C6 и внутренних данных (C2).

| Метрика | Что показывает | Цель | Метод проверки |
| --- | --- | --- | --- |
| Recall C4, текстовые поля | Доля найденных спецкатегорий в тексте | ≥ 99 % | Эталон, текстовая страта (800 полей) |
| Recall C4, обычные сканы | То же для сканов после OCR | ≥ 97 % | Эталон, OCR-страта (200 полей) |
| Recall C4, сложные OCR | То же для трудных сканов | ≥ 90 % | Эталон, страта «сложные OCR» (200 полей) |
| Precision C4 | Доля верных среди помеченных ПД(здоровье) | ≥ 90 % | Случайная выборка рабочего потока |
| F1 C4 | Баланс precision и recall | ≥ 0,9 | Эталон и случайная выборка |
| Recall C3 | Доля найденных общих ПДн | ≥ 98 % | Эталон, записи, договоры, кадровые |
| Precision C3 | Доля верных среди ПД(общие) | ≥ 90 % | Случайная выборка рабочего потока |
| F1 C3 | Баланс precision и recall | ≥ 0,9 | Эталон и случайная выборка |
| Recall C5 | Доля найденных платёжных полей | ≥ 98 % | Эталон, платёжная страта |
| Precision C5 | Доля верных среди ПД(фин.) | ≥ 90 % | Случайная выборка рабочего потока |
| F1 C5 | Баланс precision и recall | ≥ 0,9 | Эталон и случайная выборка |
| Recall C6 | Доля найденных секретов (ключи, пароли, токены) | ≥ 99 % | Синтетические примеры и сканер секретов |
| Precision C6, F1 C6 | Точность и баланс по секретам | ≥ 90 %, ≥ 0,9 | Синтетические примеры |
| Precision, recall и F1 для внутренних данных (C2) | Качество на негативной страте | ≥ 90 %, ≥ 90 %, ≥ 0,9 | Эталон, негативная страта (300 полей) |
| Каппа Коэна | Согласованность разметчиков на эталоне | ≥ 0,8 | Эталон при каждом пополнении |
| Доля полей в карантине | Поля без тега или с низкой уверенностью | < 2 % | Экспортёр метрик (поля «в очереди на классификацию» не входят) |
| Возраст самого старого поля в карантине | Не копится ли неразобранное | ≤ 2 рабочих дней (SLA ревью) | Экспортёр метрик |
| Доля таблиц с владельцем и тегом | Полнота каталога | 100 % | Выгрузка из OpenMetadata |
| Доля C4-полей, ошибочно маршрутизированных в зону ниже Restricted | Ошибки маршрутизации | 0 | Аудит загрузчика, алерт |
| Доля полей с пустым тегом в аналитике | Непомеченные поля в витринах | 0 | Проверка тегов в ClickHouse |
| Доля выгрузок с k < 5 | Нарушение k-анонимности | 0 | Проверка при экспорте |
| Полнота OCR для C4-источников | Доля распознанных страниц | ≥ 95 % | Счётчик нераспознанных страниц в staging |
| Доля изменённых полей схемы на пакет | Дрейф схемы | алерт при > 5 % | Реестр схем (E4) |
| Время реакции на дрейф схемы | От обнаружения изменения до переклассификации | < 1 рабочего дня | Метки времени в реестре схем (E4) |
| Latency классификации пакета (p95) | Время от поступления до размеченной загрузки | ≤ 60 мин | Трассировка событий |
| Throughput | Скорость классификации | ≥ 50 000 строк/мин для правил; NER ≥ 200 полей/мин | Нагрузочный прогон на staging |

Ежедневный выборочный аудит: steward случайно проверяет 0,5–1 % полей, которые классификатор разметил с уверенностью выше порога. Без этого шага ошибки с уверенностью 0,95 никогда не попадут в ревью. По итогам аудита пересчитывается production recall: доля ошибок в аудитной выборке переносится на весь поток с доверительным интервалом. Найденные ошибки возвращаются в эталон. Нагрузка на одного steward: при 3 млн строк в сутки аудит по полям C3–C5 охватывает сотни полей, поэтому выборка берётся по полям, а не по строкам, и ограничивается 300 полями в день до появления второго разметчика.

Пороги уверенности по классам задаются явно, а не подбираются только по кривой:

| Класс | Порог уверенности | Действие ниже порога |
| --- | --- | --- |
| C4 (ПД(здоровье)) | 0,85 | Поле в карантин, не в Restricted |
| C5 (ПД(фин.)) | 0,80 | Поле в карантин |
| C3 (ПД(общие)) | 0,75 | Поле в карантин |
| C2 (Внутренние) | 0,70 | Поле в карантин |
| C1 (Публичные) | 0,70 | Поле в карантин |

Пониженный порог для C4 означает, что классификатор пропускает в аналитику только то, в чём достаточно уверен. Поле, набравшее 0,84 по C4, уходит в карантин, а не в Restricted. После ревью steward порог пересматривается по накопленным данным через кривую recall/карантин. Пороги версионируются вместе с правилами в реестре версий (E10).

Recall считается по эталону, precision — по случайной выборке рабочего потока, а не по стратифицированному эталону: соотношение классов в нём намеренно искажено, и переносить precision на прод некорректно.

## 6. Масштабируемость

Базовый объём и целевые значения после пятикратного роста:

| Параметр | Сейчас (оценка) | После ×5 | Как получено |
| --- | --- | --- | --- |
| Строк через классификатор в сутки | 600 000 | 3 000 000 | Допущение: полный ночной дамп БД портала, выгрузки 1С и реестра, а не только дельта. Дельта по Task4 — единицы тысяч строк в сутки; уточняется замером на staging |
| Сканы в сутки | 6 000–9 000 страниц, 2,4–3,6 ГБ | 30 000–45 000 страниц, 12–18 ГБ | Task4: 0,6–0,9 ТБ в год, ×5 = 3–4,5 ТБ в год |
| Текстовых полей для NER в сутки | 1 500–2 000 | 7 500–10 000 | 0,25–0,3 % строк содержат свободный текст |
| Аналитиков и steward | 3 | 15 | Допущение, в условиях задачи не задано |
| Запросов к query gateway, в секунду | 5 | 25 | Оценка по числу отчётов и пользователей |

Объём данных (рост в 5 раз):

- Пакеты делятся по партициям источника (таблицы, дни, филиалы). Каждая партиция классифицируется независимо и параллельно.
- Воркеры классификатора запускаются в Kubernetes с горизонтальным автомасштабированием по CPU и по числу необработанных партиций. Автоскейлинг по длине очереди не используется: очередь Kafka стоит после маршрутизатора по зонам (E6), а не перед классификатором (E5).
- Полная классификация только для новых и изменённых полей. Остальные используют сохранённый результат по хэшу схемы и содержимого.
- Для больших таблиц оценка качества идёт по выборке (1 % строк), но разметка перед записью в зоны выполняется по всем строкам. Выборочная классификация пропускает редкие значения в свободном тексте и ломает цель recall ≥ 99 %. Полный проход обязателен для записи в зоны, а выборка нужна только для предварительной оценки и профилирования.
- ClickHouse масштабируется шардированием по филиалу или по дате. Зоны Restricted и Pseudonymized живут на отдельных шардах.

Рост числа пользователей и филиалов:

- Query gateway и сервис политик stateless и масштабируются репликами за балансировщиком.
- Политики OPA кешируются у точек применения. Изменение политики расходится событием, без опроса.
- Новые филиалы добавляются как новые партиции и источники без изменения схемы движка.

Надёжность при росте:

- Загрузчик идемпотентный: повторная загрузка пакета не создаёт дубликатов (проверка по контрольной сумме пакета).
- Очередь между классификатором и загрузчиком сглаживает пики нагрузки.
- При отказе классификатора пакет уходит в очередь повторов до классификации, а не в карантин. В хранилище без тегов он не попадает.

Пока классификатор недоступен, сырой пакет остаётся в staging и в очереди повторов. TTL staging 24 часа на этот случай не хватает, поэтому очередь повторов хранит копию пакета до классификации отдельно, с TTL 7 дней. Если простой затянулся дольше 24 часов, staging-копия истекает, а пакет восстанавливается из очереди повторов; если истекли оба срока, пакет перезабирается из источника и помечается как повторный. Разметка при этом не теряется: результат хранится по хэшу пакета.

Смена тега поля при переклассификации — это перевод между зонами, а не правка на месте. Поле удаляется из старой зоны мутацией, записывается в новую с новым DEK, а в журнал классификации попадает пара «старый тег → новый тег» с версией правил. Выгрузки, сделанные до переклассификации, помечаются в каталоге как устаревшие.
