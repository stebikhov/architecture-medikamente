# Задание 3. Стратегия защиты данных: Шифрование при хранении и при передаче

Связанные материалы: [../Task1/problems.md](../Task1/problems.md) (As-Is и проблемные зоны), [../Task2/c4-target.drawio](../Task2/c4-target.drawio) (целевая архитектура с PbD-слоями).

В документе закреплена классификация данных по категории «Медикаменте» и прописаны меры их защиты. Маркирование и распределение по зонам используют эту же шкалу — отдельной шкалы не вводят.

### 1.2. Теги (единая шкала для файлов, записей и колонок)

У каждого класса один тег. В тексте и на диаграммах тег пишем по-русски, а в правилах и конфигурациях (§7) — машинным идентификатором. Пустой тег значит «не классифицировано» и никогда не считается внутренними данными (правило «по умолчанию конфиденциально»).

| Тег (читаемое имя) | Идентификатор в системах | Расшифровка                                    | Класс | Где применяется                                  |
| ------------------ | ------------------------ | ---------------------------------------------- | ----- | ------------------------------------------------ |
| Публичные          | `pd:public`              | Публичные данные, не ПДн                       | C1    | Витрины, справочники услуг                       |
| Внутренние         | `internal`               | Внутренние данные без ПДн                      | C2    | Расписания, ТМЦ, регламенты                      |
| ПД(общие)          | `pd:general`             | Общие персональные данные                      | C3    | Журналы записей, договоры, карточка клиента      |
| ПД(здоровье)       | `pd:special`             | Специальная категория ПДн: сведения о здоровье | C4    | Медкарты, анализы, заключения, анкеты о здоровье |
| ПД(фин.)           | `pd:financial`           | Платёжные и финансовые данные                  | C5    | Платёжные операции, чеки, проводки               |
| Секреты            | `pd:secret`              | Ключи, пароли, токены доступа                  | C6    | Ключи, пароли, токены                            |

Префикс `pd:` в идентификаторах — от personal data. Схема соглашения проектная, внешнего стандарта за ней нет.

### 1.3. Зоны хранения

Привязаны меры защиты по зонам.

| Зона                         | Классы                                                | Кто имеет доступ                                                                                                |
| ---------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Staging** (вне ClickHouse) | сырые пакеты до классификации, TTL 24 часа            | Только загрузчик и сервисная роль движка                                                                        |
| **Landing** (в ClickHouse)   | пакеты после классификации, до маршрутизации по зонам | Только загрузчик и Data steward (специалист по качеству и классификации данных), steward — в маскированном виде |
| **Restricted**               | C4, C5 и прямые идентификаторы C3                     | ABAC через PDP, доступ по обоснованию цели обработки                                                            |
| **Pseudonymized**            | C3 (с токенами вместо ПДн), C2                        | Аналитики по роли, через query gateway                                                                          |
| **Anonymized**               | агрегаты, k-анонимные выборки                         | Широкий круг пользователей                                                                                      |
| **Карантин**                 | не классифицировано / низкая уверенность              | Только Data steward, маскированный просмотр; аналитикой не используется                                         |

Псевдонимизированными данными(зseudonymized) остаётся ПДн: временный псевдоним(patient_token) можно связать с человеком через сервис токенов, поэтому правила те же, что для C3. Псевдонимизацию и k-анонимность мы не считаем обезличиванием по приказу РКН № 996, это только мера снижения риска. Обезличенными называем лишь агрегаты, которые прошли методы из этого приказа.

Зона Anonymized определена как агрегаты, но публичные данные (C1) ПДн не содержат и могут лежать там без псевдонимизации. Для C1 зона по умолчанию — «Anonymized / без ограничений».

| C1    | в покое и в передаче                                                        | 2   | 1   | 2    |
| C2    | в покое (Excel, 1С на общем диске)                                          | 3   | 2   | 6    |
| C3    | в покое (Excel, сканы, 1С), в передаче (Outlook, файловый доступ)           | 4   | 4   | 16   |
| C4    | в покое (сканы, PDF, JPG на общем диске), в использовании (ресепшен, врачи) | 5   | 5   | 25   |
| C5    | в передаче (TCP/IP к ККМ, OLE), в покое (Excel двойного учёта)              | 4   | 4   | 16   |
| C6    | в покое и в конфигурациях (скрипты, файлы настроек)                         | 3   | 5   | 15   |

Отдельно посчитаны риски целостности и доступности:

| Риск                                                                     | В   | У   | Риск | Класс данных |
| ------------------------------------------------------------------------ | --- | --- | ---- | ------------ |
| Потеря/подмена медкарты из-за отсутствия аудита и контроля целостности   | 4   | 5   | 20   | C4           |

Остаточный риск после мер (оценка на текущем этапе): C4 — 25 → около 8 (шифрование, ABAC, аудит, но остаются инсайдер и ошибки врачей), C3 и C5 — 16 → 6–8, C6 — 15 → 5, C2 — 6 → 3. Единая точка отказа снижается только после резервирования сервера, поэтому её остаток пока высокий.

## 3. Классификация по состоянию

- **При хранении:** файлы на общем диске, файловые базы 1С, Excel, резервные копии, озеро данных (Staging, Landing, Restricted, Pseudonymized, Anonymized).
- **In transit (передача):** запросы к порталам, API-контракты, связь с ККМ по TCP/IP, OLE-вызовы 1С, почта Exchange, выгрузки в налоговую, будущая интеграция с лабораторией.
- **In use (обработка):** экраны ресепшена и врачей, отчёты BI, обучение ML и LLM. Шифрование тут не помогает, поэтому нужны маскирование, ABAC и аудит.

| ----- | ----------------------------------------------- | ------------------------------------------ | ------------------------------------------------------ |

| C2    | разграничение по папкам/схемам, шифрование тома | TLS / SMB 3.1.1                            | доступ по роли                                         |
| C3    | полевое шифрование AES-256-GCM, шифрование тома | TLS 1.2+, mTLS внутри кластера             | маскирование, ABAC, аудит чтений                       |
| C4    | полевое шифрование через KMS, отдельный контур  | mTLS, mTLS с лабораторией                  | маскирование для ресепшена, ABAC, аудит каждого чтения |

## 5. Стратегия шифрования

### 5.1. Шифрование при хранении

- **Алгоритм:** AES-256-GCM. Где нужна сертифицированная отечественная криптография — «Кузнечик» (ГОСТ Р 34.12-2015).
- **Слой шифрования.** GCM — AEAD-режим, а `pgcrypto` AEAD не поддерживает, поэтому основное шифрование делается в приложении или в HSM/KMS.
  - `encrypt_iv`/`decrypt_iv` работают в режиме CBC, `pgp_sym_encrypt` — OpenPGP/CFB с AES-128 по умолчанию; AES-256 требует явного `cipher-algo=aes256`.
  - `pgcrypto` — только дополнительный слой для отдельных полей C3/C5; ключи и открытые данные при этом проходят через СУБД.
- **Секреты.** C6 в базе не хранятся: они лежат в OpenBao/HSM и подставляются приложению при запуске.
- **Уровни:**
  - диск сервера: BitLocker (Windows) или Secret Net (сертифицирован ФСТЭК) — полное шифрование тома;
  - СУБД: шифрование томов БД на уровне ОС (dm-crypt/LUKS) плюс поля; TDE опционально, только если будет коммерческий дистрибутив PostgreSQL с лицензией (в open source его нет), проект на него не рассчитан;
  - ClickHouse: шифрование томов и прикладное шифрование колонок C4/C5 через KMS; `storage_policy` только выбирает тома и ничего не шифрует, так что шифрование диска настраивается отдельно; staging вне ClickHouse — SSE-KMS;
  - файлы и документы: шифрование на уровне приложения перед записью в хранилище;
  - резервные копии: Veeam или отечественная СРК с AES-256.
- **Ключи:** envelope encryption. Данные шифруются ключом DEK, DEK шифруется мастер-ключом KEK в KMS или HSM. KEK из HSM не выходит.
- **Nonce в AES-GCM:** 96-битный, случайный или счётчик, на одном DEK nonce не повторяется никогда. Число сообщений на один DEK ограничиваем (для случайного nonce порядка 2^32), после лимита DEK ротируем.
- **Ротация:** KEK — на зону хранения, раз в год или по инциденту. DEK — на субъекта (нужно для криптошрединга при DSAR) либо на объект/версию пакета, ротация при каждом перешифровании. Компрометация одного DEK остальные данные не раскрывает.
- **Криптошрединг и C4.** Удаление DEK для медкарты до конца срока хранения (25 лет) не делаем: удалять её нельзя. По запросу пациента на удаление для C4 прекращаем обработку и ограничиваем доступ (152-ФЗ ст. 21 ч. 5), а DEK уничтожаем после срока хранения. Для C3 без обязательного хранения криптошрединг применяется сразу.
- **Разделение доступа:** администратор СУБД к KEK доступа не имеет, он есть только у сервиса шифрования по роли.

### 5.2. Шифрование in transit

- **Внешние каналы:** TLS 1.2+ (TLS 1.3 по умолчанию) для порталов, API и провайдера оплаты. HSTS на всех публичных доменах.
- **Внутренние каналы:** mTLS между сервисами в Kubernetes (Istio или Linkerd), сертификаты выпускаются и ротируются автоматически.
- **Офис и сеть:** ViPNet для филиалов и удалённых сотрудников, SMB 3.1.1 с шифрованием для общих папок, LDAPS вместо LDAP, Exchange только по TLS.
- **Касса и ККМ:** ККТ IPsec и ViPNet не поддерживают, поэтому отдельный VLAN для касс, ACL на межсетевом экране, при необходимости шлюз перед кассами.
- **Лаборатория (фаза 2):** mTLS с проверкой сертификата лаборатории и подписью сообщений.
- **Требование ГОСТ:** при обязательном ГОСТ-TLS для госинтеграций — КриптоПро NGate.

### 5.3. Обфускация и обезличивание в состоянии in use

- **Маскирование** на уровне запросов: ресепшен видит `Иванов И. И.`, врач полное ФИО, аналитик токен.
- **Псевдонимизация:** в CRM, BI и ML вместо ФИО токен пациента. Зона Pseudonymized остаётся ПДн, обезличиванием по приказу РКН № 996 это не считается.
- **k-анонимность:** для выгрузок k ≥ 5, квази-идентификаторы (возраст, район, диагноз) обобщаются. Тоже снижение риска, а не обезличивание по № 996.
- **Дифференциальная приватность:** для агрегатов, уходящих в LLM и внешним партнёрам.
- **Обезличивание** в смысле приказа № 996 — только отдельная процедура (методы по приказу, например агрегирование), её результат кладём в Anonymized.
