### 1.1. Новые блоки, которых нет в As-Is

1. Privacy-контур. Сквозной слой: PDP и PEP, Сервис тегирования, Сервис токенов, Сервис согласий, Служба сроков и удаления, Служба аудита, KMS/HSM, Сканер меток и DLP, Мониторинг.
2. Аналитический слой с PbD. Озеро с зонами по уровню защиты, Staging, движок классификации на входе, карантин, каталог и lineage, query gateway с маскированием.
3. Сервис уведомлений. Для MVP обязателен: напоминание о приёме за день пациенту и врачу. Сейчас напоминания делаются вручную.
4. Сервис согласий — технический учёт согласий.

Правило проверки доступа на диаграмме: PEP стоит на входе API, это первый рубеж. Row-level security (RLS, ограничение строк средствами БД) в PostgreSQL — второй рубеж. KMS отдаёт только ключи, данных не читает. Поэтому прямые связи «Система записи → PostgreSQL / Сервис токенов / Сервис согласий» и «KMS → PostgreSQL» не обходят PEP: на них подписан порядок проверки.

### 2.2. Матрица доступа

`branch` — филиал сотрудника. Ресепшен и врач работают только в своём филиале.

| Категория                               | Домен  | Роли (RBAC)                                                     | Атрибуты (ABAC)                                                                                              | По умолчанию                         | Аудит                             |
| --------------------------------------- | ------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------ | --------------------------------- |
| C1 Публичные — прайсы, графики          | D6     | Все сотрудники                                                  | —                                                                                                            | Разрешено                            | Нет                               |
| C2 Внутренние — расписание, ТМЦ         | D6, D1 | Ресепшен, склад, бухгалтерия; врач — расписание и журнал приёма | Врач: `appointment_id ∈ мои приёмы`                                                                          | По роли                              | Чтение                            |
| C3 ПД(общие) — журнал записей, договоры | D1, D4 | Ресепшен, пациент, бизнес-аналитик (D4, только токены)          | Ресепшен: `branch = свой`, `purpose ∈ {appointment, contract}`; пациент: `patient_token = свой`              | Запрет, нужна цель                   | Каждое чтение                     |
| C3 ПД(общие) — кадровые данные          | D7     | Бухгалтер, руководитель подразделения                           | `branch = свой`, `подразделение = своё`; сотрудник видит свой листок                                         | По роли                              | Каждое чтение                     |
| C4 ПД(здоровье) — медкарты, анализы     | D2     | Врач, пациент, медицинский руководитель                         | Врач: `appointment_id ∈ мои приёмы`, `purpose = treatment`, `branch = свой`; пациент: `patient_token = свой` | Запрет без цели; ресепшену запрещено | Каждое чтение, алерт при массовом |
| C5 ПД(фин.) — платежи, чеки             | D3     | Кассир, бухгалтер                                               | Кассир: `смена = текущая`, `branch = свой`; бухгалтер: `branch = свой`, чтение без выгрузки                  | По роли                              | Каждая операция                   |
| C5 — данные карты                       | D3     | Платёжный шлюз (сервисная роль)                                 | —                                                                                                            | Не хранится, только токен            | Каждая операция                   |
| Производные от C3–C4 — BI, ML, LLM      | D5     | Аналитик                                                        | BI и ML: `зона = anonymized`; LLM: `зона = anonymized`, `k ≥ 5`; Pseudonymized — по отдельному решению       | Только обезличенные витрины          | Каждый запрос                     |
| C6 Секреты — ключи, пароли              | D8     | Сервисная роль                                                  | —                                                                                                            | Доступ по секрету, человек не читает | Каждое получение                  |

Замещение врача. Если врач отсутствует, доступ получает заместитель одним из двух способов. Первый: заместителю назначают конкретные `appointment_id` на период отсутствия, остальные правила C4 не меняются. Второй, экстренный (break-glass — доступ в обход обычных правил по заявке): нужны заявка, подтверждение двух человек (двух ключей), срок действия и журнал.

## 4. Границы MVP и последующих фаз

| Фаза            | Состав                                                                                                                                                                                                 | Диаграмма |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------- |
| MVP (неделя 13) | Портал клиента и ресепшена, система записи, сервис уведомлений (пациенту, врачу, ресепшену), IAM, минимальный Privacy-контур (PDP, PEP, согласия, аудит, KMS), базовый CI/CD-гейт                      | Стр. 1, 2 |
| Ф2              | CRM (неделя 20), платёжный контур (неделя 33), миграция медкарт и анализов (неделя 39), озеро данных, BI, движок классификации, лаборатория, мобильное приложение, DLP (пилот), расширенный CI/CD-гейт | Стр. 1, 2 |
| Ф3              | Голосовой робот, аудит нетипичных действий, отчётность в налоговую, ML/AI                                                                                                                              | Стр. 1, 3 |

CI/CD-гейт — автоматическая проверка релиза на корректную работу с тегированными данными. Базовая версия (MVP): сборка не проходит, если новая выгрузка или таблица не имеет тега класса, а запрос к ПД(здоровье) идёт мимо PEP. Расширенная версия (Ф2): контрактные тесты на теги, проверка, что тестовые данные не содержат реальных ПДн, SAST/SCA.

Миграция медкарт (неделя 39, Ф2): подготовка данных 30…34, тестирование 35…38 (теневой режим на 37…38), cutover на неделе 39, стабилизация 39…41. Источник истины по медкартам — PostgreSQL (контейнер «Медкарты и документы», Restricted); Restricted-зона аналитики в ClickHouse — отдельное хранилище, они не смешиваются.
